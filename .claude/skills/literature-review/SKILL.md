# Literature review

`litreview.md` (project root) is the task spec: research questions, scope notes, seed topics, required outputs. Read it first. This skill is the **how**.

- `scripts/lr.py` — helper for all routine API and bookkeeping work. **Use it instead of hand-written curl.** Run `python3 .claude/skills/literature-review/scripts/lr.py -h` (abbreviated `lr.py` below).
- `scripts/test_lr.py` — regression tests. **Run them after any change to `lr.py`** (`python3 .claude/skills/literature-review/scripts/test_lr.py`; add `LR_LIVE=1` to include live API checks). Add a test for every bug fixed.
- `references/apis.md` — raw API details (INSPIRE / arXiv / HEPData query syntax, response formats, gotchas) for anything `lr.py` doesn't cover.

## Hard constraints

- Read/write only inside `~/colorflow/`; Zotero PDFs (`$ZOTERO_STORAGE`) are read-only; `/tmp` is for temporary files only. Downloads go to `litreview/papers/` (git-ignored). Bash is sandboxed and can reach only the domains in `.claude/settings.json`; other hosts only per the network rule in CLAUDE.md.
- **Keep command output small.** Oversized outputs get persisted by the harness to `~/.claude/...`, which you may not read. Never print full INSPIRE records; avoid `--abstract` on large result sets; pipe through `head`.
- Run every `lr.py` pipeline with `set -o pipefail` (e.g. `set -o pipefail; lr.py refs 374155 | lr.py add`). Otherwise a failed upstream command looks like "added 0".
- Rate limits (INSPIRE 15 req/5 s, arXiv 1 req/3 s) are enforced by `lr.py` across processes. Don't bypass them with parallel raw curl.
- Missing full text: `lr.py fetch` marks the paper `blocked`; continue. Ask the user about all blocked papers together only when a check-in trigger fires (step 11). Never summarize from the abstract alone.

## State (all under `litreview/`)

| File | Role |
|---|---|
| `papers.jsonl` | **Source of truth**: one JSON record per paper ever considered. Edit only via `lr.py` (`add`, `set`, `setmany`, `seed`, `fetch`). |
| `papers.md`, `queue.md` | Generated by `lr.py render`. Never hand-edit. |
| `summaries/<ID>.md` | One per paper, or per tight cluster (e.g. measurement + erratum). Template below. |
| `synthesis.md` | Answers to RQ 1–4, citing summaries. Rewritten, not just appended, as understanding improves. |
| `open_questions.md` | Open questions, data/model tensions, proposed tests lacking convincing experimental validation. |
| `log.md` | Append-only, one entry per iteration: what was read, searches run, counts, decisions. |
| `review.bib` | Generated by `lr.py bibtex` (relevance ≥ 2). |
| `searches.tsv` | Auto-appended by `lr.py search` / `arxiv` / filtered `citing` / filtered `refs`: date, service, query, hit count. Check it before re-running a search. |
| `papers/` | Full texts: `<ID>.pdf`, `<ID>.txt`, `<ID>/` (arXiv LaTeX). Zotero PDFs are referenced in place, not copied. |

**Record fields** (`papers.jsonl`; `set` rejects unknown field names, so typos fail loudly): `recid` (INSPIRE record number, the internal dedup key alongside arxiv/doi), `texkey`, `arxiv`, `doi`, `year`, `collab`, `doctype`, `citations`, `title`, `type` (exp/th/pheno/review/MC), `notes`, `status`, `priority` (next/later), `relevance` (0–3, set after reading), `expect` (0–3, expected relevance set at triage), `rqs` (list like `["1b","3"]`), `reason`, `via` (how it was found), `fulltext` (source), `summary` (path), `zotero` (PDF paths), `bibkey`.

**Status lifecycle:** `candidate` (found, not triaged) → `queued` | `rejected`; `queued` → `read` (full summary) | `skimmed` (full text examined, judged low relevance; a short summary or a `reason` suffices) | `rejected` | `blocked` (no full text); `blocked` → `queued` when a PDF turns up (`fetch` or `seed --bib`).

**ID:** INSPIRE texkey (e.g. `CDF:1994zkl`) for humans; in filenames `:`→`_` (`summaries/CDF_1994zkl.md`). `lr.py` computes this and accepts recid, texkey, file ID (`CDF_1994zkl`), arXiv id, DOI or Zotero bibkey wherever an ID is expected.

### Summary template

```markdown
# <Title>
- **ID / links:** <texkey> · INSPIRE <recid> · arXiv <id> · DOI <doi>
- **Authors / collab, year, journal:**
- **Type:** experimental | theory | phenomenology | MC/model | review
- **Relevance:** 0–3 · RQs: …
- **Full text source:** zotero | arxiv | arxiv-latex | inspire-doc
## Takeaways
<≤5 bullets: what the synthesis needs from this paper>
## Setup
<collider, √s, process, observables, selections, models compared, approximations>
## Results
<quantitative, each claim anchored: (Fig. 3), (Tab. 2), (Eq. 4.1), (p. 7). Which models describe the data and which fail, and by how much.>
## Assessment
<our view, kept separate from the authors' claims: robustness, caveats, model dependence, tensions with other papers>
## Leads
<specific references / follow-ups worth queueing, each with a reason>
```

## The loop

Each iteration:

1. **Load state.** `lr.py list --status queued --priority next`, `tail` of `log.md`. First run only: `lr.py seed` (resolves `human_start.bib` to INSPIRE records with Zotero PDF paths, status `queued`/`next`; entries flagged `match: title-search: verify` need a manual check), then run at least one INSPIRE search per seed topic in `litreview.md`, piped into `lr.py add`.
2. **Pick a batch** of ~5–15 from "Next" (`list` ranks by `expect`, then `nvia`, then citations); group related papers so one reader handles a cluster. Early on, favour reviews (`tc r`) — they map the field and their reference lists are high-yield.
3. **Get full text:** `lr.py fetch <ID>` (Zotero → arXiv PDF → INSPIRE-attached scan → OpenAlex open-access PDF; add `--source` for arXiv LaTeX on theory papers). Stale Zotero paths (e.g. from another machine) are looked up again under `$ZOTERO_STORAGE` by attachment key and saved; if the PDF isn't there, the downloads are tried. It prints the PDF path and `text_layer`. If no source works it marks the paper `blocked` and prints any publisher `urls` and OpenAlex `oa_url` (usually a landing page). Check those by hand for a free PDF (e.g. CDS, SCOAP3); if you find one, download it to `litreview/papers/<ID>.pdf` and re-run `fetch` (an existing file there is reused). Otherwise leave the paper blocked.
4. **Read & analyze** via subagents (see below). Readers read the **PDF itself** with the Read tool (`pages` param, ≤20 pages per call), so figures, tables and equations are visible; `<ID>.txt` is for grepping. For scans (`text_layer: false`) the PDF is the only option.
5. **Record results** in one call: `lr.py setmany` with one line per paper, e.g. `CDF:1994zkl status=read relevance=3 rqs=1b,3 type=exp summary=summaries/CDF_1994zkl.md` (use `skimmed` / `rejected` with `reason="…"` as appropriate). It is all-or-nothing: on any error nothing is saved.
6. **Expand the frontier**, with caps:
   - **Backward** (relevance ≥ 2): `lr.py refs <recid> | lr.py add`. For long reference lists (reviews, > ~150 refs) use topical subsets instead, e.g. `lr.py refs <recid> --filter "t reconnection" | lr.py add`, one call per topic. The first 15 unresolved references are listed on stderr (`--show-unresolved N` for more); look up important-looking ones by hand.
   - **Forward** (relevance 3, or relevance 2 reviews): `lr.py citing <recid> --limit 30` (most-cited) **and** `--sort mostrecent --limit 15`. If the paper has > 300 citations, use `--filter "t reconnection"`-style topical filters (no parentheses) instead of taking the top-N blindly.
   - Always pipe expansion output straight into `lr.py add`, **not** through `lr.py new` first. `add` deduplicates by itself and appends the `via` link to papers already known. The producers label each record automatically (`ref of recid:N`, `cites recid:N`, `search: <query>`, `arxiv: <query>`), so no `--via` is needed. `nvia` counts distinct `ref of`/`cites` links (searches and seeds don't count) and is the main triage ranking signal; filtering with `new` first would throw it away. Never print raw `refs`/`citing` output for large papers.
   - **Keyword:** `lr.py search 't "string effect" and date > 1985'` and `lr.py arxiv 'abs:"color reconnection" AND cat:hep-ph'` for terms met while reading and for seed topics. Run `lr.py arxiv` mainly for preprints too recent for INSPIRE.
   - Everything enters as `candidate` (deduplicated automatically against recid/arXiv/DOI/texkey/bibkey). Use `lr.py new` only to preview what would be new.
7. **Triage candidates.** Expect hundreds per iteration, too many to read in the orchestrator's context. `lr.py list --status candidate` is ranked by `nvia` (how many reviewed papers point to a candidate; a strong signal) and then by citations, and is paginated (`--limit 40 --offset N`).
   - Up to ~40 candidates: triage directly with `lr.py list --status candidate --abstract`.
   - More than that: fan out triage subagents, one per page of 40. Each runs `lr.py list --status candidate --abstract --limit 40 --offset N`, reads `litreview.md` for scope and the "Triage heuristics" section of this skill for the relevance scale, and **returns** `setmany` lines (`<ID> status=queued priority=next|later expect=N reason="…"` or `status=rejected reason="…"`) without running them. The orchestrator applies all returned lines in one `lr.py setmany` call. Don't run `add` while triage subagents are working: the page boundaries would shift.
   - Rejected papers stay in the DB so they are never re-triaged.
8. **Verify:** for each new relevance-3 summary, a separate subagent checks every quantitative claim against the cited figure/table/page and fixes or flags discrepancies.
9. **Update docs:** revise `synthesis.md` and `open_questions.md` from the summaries' *Takeaways* (once there are > ~30 summaries, delegate this to a dedicated subagent given the list of new/changed summaries plus the current synthesis). `lr.py render`; `lr.py bibtex`; append to `log.md`.
10. **Commit:** `git add -A && git commit -m "litreview iteration N: <short summary>"`.
11. **Check in / converge.**
   - **Check-in triggers.** Stop and ask the user when any of these holds: ≥ ~10 papers are `blocked`; any blocked paper has `expect=3`, not counting papers the user has confirmed unobtainable (`notes="inaccessible: …"`; list these as gaps in `open_questions.md`); ~150 papers have been read in full since the last check-in (record each check-in in `log.md` as a line `CHECK-IN: <date>, <n> papers read so far`, so the count is recoverable). Otherwise report progress briefly (read, key findings, queue size, blocked count) and continue.
   - **At a check-in,** list the blocked papers (`lr.py list --status blocked`) with title, DOI and why each matters. Ask the user to download them into Zotero and export them as biblatex to `litreview/zotero_<date>.bib`. Then `lr.py seed --bib litreview/zotero_<date>.bib` attaches the PDFs and moves those papers from `blocked` back to `queued`. Check each attached PDF's first page against the paper: Zotero can attach the wrong file. Papers the user cannot obtain stay `blocked` with `notes="inaccessible: <reason>, <date>"`.
   - **Convergence.** Stop expanding when, in two consecutive iterations, fewer than ~10% of newly triaged candidates get `expect` ≥ 2, and every RQ has theory + experiment coverage across eras (PETRA/PEP, LEP, Tevatron, HERA, LHC, EIC projections).

### Triage heuristics

- Relevance: 3 = directly measures/models coherence, CR or color flow, or proposes a test; 2 = important context, method, or prerequisite; 1 = tangential; 0 = out of scope.
- Scope follows `litreview.md` (small-system collectivity is in; generic heavy-ion flow is out unless connected to CR/ropes/coherence).
- Experimental papers: check HEPData (see `references/apis.md`); a record + Rivet analysis means the measurement is actively used in MC tuning.
- Citation count is not decisive — recent proposals for tests (RQ4) have few citations.

## Subagents

Fan out reading. Each reader gets:
- paper ID(s) and the full-text paths from `lr.py fetch` output;
- the research questions (or tell it to read `litreview.md`), the summary template (point it to the "Summary template" section of `.claude/skills/literature-review/SKILL.md`) and the target path `litreview/summaries/<ID>.md`;
- instructions: stay inside `~/colorflow/`; read the PDF (figures matter); anchor every quantitative claim; keep authors' claims separate from assessment; if the full text is unreadable, report back rather than guess; return the relevance score, RQs, type, and a list of leads with reasons.

`lr.py` holds a lock around every write to `papers.jsonl`, so parallel calls are safe. Still, only the orchestrator runs `lr.py add/set/setmany/seed/render/bibtex`, edits `synthesis.md` / `open_questions.md` / `log.md`, and commits. Subagents write only their own summary files. Frontier expansion (API queries) stays in the orchestrator.
